# 2026-09-11 · G11 and G26 leave lens 6, which now computes nothing

**Decided by KH:** *"G26, G11은 삭제하는게 맞을거 같아."* Both numbers are
vacant and neither is reused. Lens 6 keeps **G23, G24, G25, G27** — three
`hard` and one `bias`, all of which read another lens's verdict or a
declaration. `LIMITS` is empty. **The lens computes nothing at all**, which is
the honest description of what it was already mostly doing.

## G11 — the formula did not describe this instrument's measurement

G11 was the one quantity lens 6 computed rather than reviewed:

```
relative_error   = 1 / sqrt(N_p x N_f)
margin           = (N_p x N_f) / (1 / target^2)
```

`validity/power.py` states the assumption in its own docstring — *"particles
are independent, so N_p x N_f counts independent samples. In a crowded or
hydrodynamically coupled suspension they are not, and this is optimistic."*
**A single trapped bead is the worse case the docstring does not name, because
consecutive FRAMES are correlated too.**

For the drag calibration this instrument is being set up for:

| | |
|---|---|
| 1 bead, 520 fps, 60 s | `N_p × N_f = 31,200` |
| τ = γ/κ = 0.04675/3.87 | **12.1 ms**, so **6.3 frames per relaxation time** |
| independent samples ≈ N_f/(2·6.3) | **≈ 2,480** |
| G11 reported | **0.566%**, margin **78×**, ROUTINE, `advances: True` |
| defensible | **≈ 2.0%**, margin **≈ 6×** |
| overstatement | **3.5×** |

The verdict did not flip — 2.0% still clears a 5% target — but a gate whose
margin is wrong by 3.5× on the experiment it will most often see is not
measuring what it claims to. And the deeper problem is that **a Stokes-drag
calibration's precision does not come from `N_p × N_f` at all**: it comes from
the number of velocity steps. `κ = γv/x_eq` is fitted across commanded
velocities, and the frames within one step are averaged, not counted.

**The arithmetic survives, as a calculator.** `validity/power.py` is unchanged
and `python -m validity.cli power` still prints the floor, with the "this is a
floor" caveat it always carried. `tests/test_validity.py`'s 11 tests still
cover it. That is where a `1/sqrt(N)` bound belongs — something you consult,
not something that certifies. Same treatment `stability/drift.py`'s
`total_drift_nm` got the day before.

## G26 — a hard gate on a boolean nobody verifies

G26 read `despeckle_enabled` (plus `nonlinear_filters`) and hard-FAILed when
the intended quantity needed pixel-value linearity. Two things were wrong.

**The input was a self-declaration about a state that has never been
recorded.** This file's own agent brief said so: *"the current camera's PP state
has never been recorded"*, and `data/detectors.yaml`'s Kinetix entry has no
`post_processing:` block at all. A hard gate whose input is an unaudited
boolean cannot fail correctly in either direction.

**And the bias is already caught where it does damage.**
`detection/recommend.py` refuses a reference frame shot with despeckle on, and
puts it more sharply than G26 did:

> `despeckle on -> the ADU->electron conversion is invalid, full stop`

That refusal lands at the point where the filter destroys something computable
— deriving a photon budget from the frame — rather than at committee level on a
flag. `detection/cli.py` also carries `--despeckle-unchecked`, which flags every
number derived from an unverified frame. So lens 2 owns it, with a verified-or-
flagged path that lens 6 never had.

**`docs/06` C1 is unchanged as a pitfall.** What changed is which code owns it,
and `docs/06`'s coverage table now says lens 2 rather than lens 6.

## What went with them, and one of those is a real improvement

- **`missing.target_error` and `missing.sample_size`** — two of Phase 0's four
  refusals. The agent brief had recorded this as a divergence to report: a
  missing target error suppressed the bias review too, because **Phase 0 is
  all-or-nothing**, and the brief argued the bias review should proceed
  independently. That case can no longer arise. Phase 0 now refuses on two
  things: no upstream verdicts, and no intended quantity. (The mechanism is
  still there for a future gate to trip over — lens 8 hit the same wall the day
  before.)
- **`ValiditySetup.resolved_n_particles`** — the property that read lens 4's
  G19 `geometry.count_in_field`. ⚠ **This was the only code path carrying a
  particle count between lenses**, so `docs/01 §4`'s ROI-versus-statistics
  constraint (3 ↔ 6) now has **no computational half**. Shrinking the ROI to buy
  frame rate still cuts the particle count by the same factor —
  `roi_speed_tradeoff(0.25, 4.0) == 1.0`, an exact wash — and nothing in the
  committee notices. Recorded in `docs/01`'s cross-lens table, in `docs/04 §7`'s
  coverage row, and as an instruction in the agent brief to raise it manually.
- **`LIMITS`** — `linearity_breaking_filters: ("despeckle",)` was this lens's
  only numeric constant. Third lens with an empty `LIMITS`, after photo and
  stability, and for a third reason: this one barely computed to begin with.
- **This lens's only `soft` check.** It is now three `hard` and one `bias`.
  `soft` survives upstream in `optics.collection`, `detection.sampling` and
  `detection.snr`, so `CLAUDE.md` §2's level-3 tie-break still has work — just
  not here. (I first wrote that G11 was the committee's last `soft` check; it
  was not, and the registry snapshot says so.)

**`"linearity"` stays in `QUANTITY_REQUIREMENTS`** with no reader, deliberately:
`BIAS_SCOPE` intersects against it, and that is what scopes a photobleaching
bias to the photometric quantities rather than to everything. A comment and a
test say it is not a check.

## Falsifier

**For G11:** an experiment on this instrument whose precision really is set by
`N_p × N_f` over independent particles — a dilute ensemble MSD with no
hydrodynamic coupling, judged at short lags where most frames contribute. Then
the formula describes the measurement and a gate on it is the right shape; the
argument above turns on the single-trapped-bead case being the common one here,
which `kb/expertise/microrheology-standard-conditions.md` supports ("just want
to watch a single particle") but which is a statement about current practice,
not about the instrument.

**For G26:** somebody records the camera's post-processing state as a measured
fact rather than a declaration — reading the PVCAM properties into
`data/detectors.yaml` the way the readout modes already are. Then the input is
verified, a gate on it can fail correctly, and lens 6 reviewing it is no longer
double-charging lens 2. Note this would be a genuine improvement independent of
the gate: `detection/cli.py --despeckle-unchecked` exists because nobody has
done it.
